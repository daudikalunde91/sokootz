# SokoTZ — Software Requirements Specification (SRS)

## 1. Purpose
Define verifiable functional and non-functional requirements for SokoTZ. This document must remain consistent with PROJECT_BRIEF.md.

## 2. User Roles
- Visitor: browse public content and search.
- Customer: manage permitted account features and interact with businesses.
- Business Owner: manage their own business profile and listings.
- Administrator/Moderator: manage users, listings, reports and platform quality according to assigned permissions.

Business Owner is also referred to as "seller" in the SokoTZ Assistant documentation. Role-based access to SokoTZ Assistant features is defined in [SOKOTZ_ASSISTANT.md](SOKOTZ_ASSISTANT.md#4-user-groups-and-access).

## 3. Functional Requirements
- FR-001: Users can register with validated information.
- FR-002: Users can log in and log out securely.
- FR-003: Users can recover access through an implemented password-reset flow.
- FR-004: Business owners can create and update their own business profiles.
- FR-005: Business owners can create, edit and remove their own products or services.
- FR-006: Visitors can search listings by name, category and supported location filters.
- FR-007: Users can view business details and contact businesses using available phone or WhatsApp links.
- FR-008: Authorized administrators can moderate listings and handle reports.
- FR-009: The system records meaningful errors and provides understandable feedback.
- FR-010: Future subscription and sponsored-listing features require separately approved requirements.

### 3.1 SokoTZ Assistant Requirements (Planned)
SokoTZ Assistant is a supporting feature of the marketplace; see [SOKOTZ_ASSISTANT.md](SOKOTZ_ASSISTANT.md) for the detailed reference. Requirements FR-011 to FR-027 continue the numbering above. **Status of all assistant requirements: Planned (documented only; not implemented, not tested).** Items marked *PROPOSED — NEEDS APPROVAL* are not approved until recorded in [DECISIONS.md](DECISIONS.md). Values shown as "PENDING" must be set by a recorded decision before the related test can be finalized.

- FR-011 [MVP]: Users can open SokoTZ Assistant from the defined entry points, send text messages, receive responses and start a new conversation.
  - Acceptance: On mobile and desktop viewports the chat opens from every entry point listed in [UI_UX_SPEC.md](UI_UX_SPEC.md); a sent message produces either a response or a defined error state; "new conversation" clears the visible messages and the conversation context sent with later requests.
- FR-012 [MVP]: The assistant accepts questions in Kiswahili and English and replies in the language of the user's message, using Kiswahili when the language is unclear.
  - Acceptance: In a reviewed test set of Kiswahili and English questions, every reply is in the language of the question; unclear-language inputs receive Kiswahili replies; Kiswahili reply quality is rated acceptable by Kiswahili-speaking reviewers against criteria defined in [TEST_PLAN.md](TEST_PLAN.md).
- FR-013 [MVP]: The assistant finds businesses, products and services by name, category and location using actual marketplace data retrieved by the backend.
  - Acceptance: For test queries with known expected records, every result named by the assistant is a record returned by the backend search operation for that request; requested filters are honored; records that are unpublished, removed or not visible to the requesting user never appear.
- FR-014 [MVP]: Each business or listing the assistant recommends is accompanied by a link, generated by the backend from the record identifier, to its actual SokoTZ page.
  - Acceptance: Every link in test responses resolves to the matching existing page; a URL written by the AI model (for example one injected through test data) is not rendered as a link.
- FR-015 [MVP]: The assistant can explain how to contact a business using only the phone or WhatsApp details published for that business and visible to the requesting user in the normal interface.
  - Acceptance: Contact details in responses match the stored published fields exactly; when none are stored the assistant says so; details not visible to the user in the normal interface are never revealed.
- FR-016 [MVP]: The assistant answers platform questions (registration, login, password recovery, business profile creation, listing creation, searching) from approved help content.
  - Acceptance: For each approved help topic the answer agrees with the approved content; for a topic not covered, the assistant states that it does not have that information instead of answering from general knowledge.
- FR-017 [MVP]: Authenticated Business Owners can ask the assistant to draft product or service descriptions, business introductions and promotional text from details they supply.
  - Acceptance: In a reviewed test set, drafts contain no price, quantity, certification or other factual claim that was absent from the owner's input (missing details appear as placeholders or questions); drafts are labelled as AI-generated; a drafting request creates or changes no listing record (database state compared before and after).
- FR-018 [MVP]: Features restricted to Business Owners (FR-017) are unavailable to visitors and to users without that role, enforced by the backend, and the assistant explains what is required.
  - Acceptance: A visitor and a Customer who request drafting receive a refusal that explains login or onboarding; direct backend calls without the role are rejected.
- FR-019 [MVP]: When the assistant cannot answer or verify an answer, it says so instead of guessing and suggests a next step.
  - Acceptance: For test questions that are out of scope or absent from help content, the response states that it cannot answer or verify and contains no fabricated specifics.
- FR-020 [MVP]: When a search returns no results, or the request is ambiguous, the assistant says so and suggests a next step without inventing alternatives.
  - Acceptance: A query with no matching records returns a no-results message and suggestions to broaden the search; any related results offered are real records returned by the backend and are labelled as related; an ambiguous location or category produces one clarifying question or a stated interpretation.
- FR-021 [MVP]: The assistant states prices, availability, ratings, reviews, locations and statistics only when they are present in retrieved data, and otherwise says they are unavailable or cannot be verified.
  - Acceptance: Test queries about data the platform does not store (for example stock levels or reviews) receive an "unavailable" answer; every price and location in test responses equals the stored value.
- FR-022 [MVP]: AI service timeouts, provider errors, malformed AI output and backend search failures produce a friendly message with a retry option and do not affect the rest of the marketplace.
  - Acceptance: With each failure simulated, the interface shows a friendly message and retry, shows no stack trace or provider detail, and the standard search and browsing features keep working.
- FR-023 [MVP]: Assistant operations apply the requesting user's authentication and authorization. Private account or business data is returned only to authorized users.
  - Acceptance: With two test users and an anonymous visitor, no assistant request, including crafted prompts and identifiers, returns another user's private data; retrieval operations run under the requester's permissions.
- FR-024 [MVP]: The backend validates assistant requests and applies rate limits.
  - Acceptance: Empty, over-length and malformed requests are rejected server-side with a clear message; exceeding the configured per-user and anonymous limits returns a rate-limit response and a clear interface message. Limit values are PENDING.
- FR-025 [MVP]: In the MVP the assistant cannot publish, edit or delete listings, change account settings, purchase or pay. Any future consequential action requires an approved workflow, server-side authorization and explicit server-enforced confirmation.
  - Acceptance: Review of the operations exposed to the assistant confirms none creates, updates or deletes marketplace or account data; tests that ask for such actions receive a decline that points to the normal screen. Tests for any future action must prove that the action cannot proceed without the confirmation step.
- FR-026 [MVP]: The chat interface tells users that responses are AI-generated and may contain errors, and gives access to information about how chat data is handled.
  - Acceptance: The notice is shown at first use and remains reachable from the chat; its text is approved before release (see open decisions in [DECISIONS.md](DECISIONS.md)).
- FR-027 [MVP — PROPOSED — NEEDS APPROVAL]: An authorized operator can disable SokoTZ Assistant through configuration without disabling any other marketplace feature. The mechanism is PENDING.
  - Acceptance: With the assistant disabled, its entry points are hidden or unavailable, assistant requests are rejected, and regression tests for other features pass.

Later enhancements (personalization, analytics explanations, user actions, human support handoff, administrator assistance) have no requirements yet and need separately approved requirements, as stated in FR-010.

## 4. Non-Functional Requirements
- Responsive and accessible user interface.
- Secure authentication and server-side authorization.
- Data integrity and appropriate validation.
- Maintainable code and documented APIs.
- Configurable deployment and environment secrets.
- Performance suitable for the agreed MVP.
- Design that allows future localization and international expansion.

### 4.1 SokoTZ Assistant Non-Functional Requirements (Planned)
The general non-functional requirements above also apply to the assistant. Status: Planned; numeric values marked PENDING or PROPOSED need approval.

- NFR-001 Grounding accuracy: No business, listing, price, location or contact detail in assistant responses may lack a matching retrieved record. Acceptance: an automated grounding check over the accuracy test set finds zero unmatched entities.
- NFR-002 Secrets: AI provider credentials exist only in backend configuration. Acceptance: a scan of the frontend bundle and the repository finds no provider credentials; example configuration contains no real secrets.
- NFR-003 Responsiveness: The interface shows a loading indicator promptly after a message is sent (PROPOSED: within 1 second) and the backend enforces a request timeout (value PENDING). Acceptance: measured in tests with a slow simulated provider.
- NFR-004 Isolation: Failure or disablement of the assistant or the AI provider must not degrade other marketplace features. Acceptance: fault-injection tests show search, browsing, login and listing management still pass.
- NFR-005 Accessibility: The chat is operable by keyboard and screen reader. PROPOSED target: WCAG 2.2 level AA. Acceptance: checks defined in [TEST_PLAN.md](TEST_PLAN.md) pass; conformance is not claimed until tested.
- NFR-006 Responsive layout: The chat is usable from 320 CSS pixels wide up to desktop widths without horizontal scrolling of the conversation. Acceptance: viewport tests.
- NFR-007 Localization readiness: Assistant interface text, help content and language handling are kept separate from code logic so languages and countries can be added without rewriting the feature. Acceptance: design review; adding a test language needs no change to retrieval or security logic.
- NFR-008 Provider replaceability: Provider-specific code is isolated behind an interface so the provider can be replaced without changing the frontend or retrieval logic. Acceptance: tests run with a fake provider; review confirms isolation.
- NFR-009 Cost control and observability: Per-user and global usage limits and a budget alert exist (values PENDING). Operational metadata (request time, outcome, error type, usage counts) is recorded without passwords, tokens or message content unless an approved retention policy allows it. Acceptance: limit and logging tests.
- NFR-010 Privacy: Only data needed for a request is sent to the AI provider. Conversation content is not stored unless an approved storage and retention policy exists. Acceptance: review of provider payloads in tests; storage tests match the approved policy.

## 5. Acceptance Criteria
Each requirement must have testable acceptance criteria. A feature is not complete merely because its page exists; its required behavior must work and be tested.

Acceptance criteria for FR-011 to FR-027 and NFR-001 to NFR-010 are stated with each requirement. Detailed test cases are in [TEST_PLAN.md](TEST_PLAN.md). An assistant requirement is not marked implemented or tested without code and recorded test results as defined in [SOKOTZ_ASSISTANT.md](SOKOTZ_ASSISTANT.md#2-status-vocabulary-and-current-status).

## 6. Error Handling
Define expected behavior for invalid forms, failed authentication, missing records, unauthorized actions, unavailable services and network failures.

For SokoTZ Assistant, the expected behavior for unknown questions, empty results, rate limits, AI provider failures and similar cases is defined by FR-019 to FR-024 and in [SOKOTZ_ASSISTANT.md](SOKOTZ_ASSISTANT.md#12-error-handling).

## 7. Scope
Separate MVP requirements from later enhancements. Do not treat proposed features as approved until a decision is recorded.

SokoTZ Assistant MVP: FR-011 to FR-027 (chat interface, platform help, grounded marketplace search, listing links, seller drafting, error handling, privacy). Everything else about the assistant, such as personalization, autonomous actions, payments, analytics explanations and human handoff, is out of the MVP until requirements and decisions are approved.

## 8. Change Control
Changes to requirements must be reflected in the relevant user flows, architecture, tests and roadmap.
